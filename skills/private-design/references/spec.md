# spec 모드 — 화면 하나 설계하기

산출물: `{YYYYMMDD}-{화면명}-spec.md`, `previews/{화면명}.html`

## Step 0 — 선행 조건

- `design/tokens.json` 이 없으면 멈추고 묻는다: "앱 전체 색 규칙이 아직 없어요. 먼저 정할까요(system), 아니면 이 화면에서 기본값(토스 스타일)으로 갈까요?" 기본값을 고르면 토스 기본 팔레트로 임시 토큰을 만들고 보고서에 "임시 토큰"이라고 적는다.
- 같은 카테고리에 PRD 가 있으면 읽는다. 유저 시나리오에 이 화면이 있으면 인터뷰 질문을 줄인다.

## Step 1 — 인터뷰

[interview](interview.md) 에서 **핵심 행동·정보량·싫은 것**을 묻는다. 그리고 화면에 들어갈 내용을 쉬운 말로 확인한다.

> "이 화면에는 ① 이번 달 쓴 돈 ② 최근 지출 5건 ③ '지출 추가' 버튼이 들어가요. 빠진 게 있나요?"

## Step 2 — 레이아웃 시안 비교

[preview](preview.md) 규칙으로 시안 2~3개를 발행한다. 색은 `tokens.json` 을 그대로 쓰고, **배치만** 다르게 한다.

- 시안 간 차이: 정보 순서, 강조할 것(큰 숫자 vs 목록), 버튼 위치(하단 고정 vs 내용 아래), 밀도
- 정상 화면 외에 **빈 상태**(데이터 0건) 1개를 반드시 함께 그린다. 사용자는 이 상태를 잊기 쉽다.

## Step 3 — 확정

사용자가 고르면 확정 시안을 `previews/{화면명}.html` 로 저장한다.

## Step 4 — 설계 문서 작성 (role design.fe 위임)

라우팅 표의 `invoke` 로 role `design.fe` 를 호출한다. 프롬프트에 아래를 전부 적는다 (codex 는 컨텍스트를 물려받지 않는다).

- 입력: 확정 시안 HTML 경로, `tokens.json` 경로, 인터뷰 요약, PRD 경로(있으면)
- 산출: `{카테고리}/design/{YYYYMMDD}-{화면명}-spec.md`
- 문서 섹션:
  - 화면 목적 (핵심 행동 1줄)
  - 텍스트 와이어프레임 (확정 시안 기준) + 참고한 패턴 1줄
  - 상태 표: loading / empty / error / success 각각의 화면 모습과 문구
  - 컴포넌트 트리 + 사용 토큰 (`tokens.json` 이름만, 색 값을 다시 적지 않는다)
  - 인터랙션: 누르면 무엇이 되는지, 오류 시 어떻게 알려 주는지
- 구조 기준: [private-tdd](../../../rules/private-tdd.md) "FE 설계 문서 적용 시" 중 화면 설계 부분

## Step 5 — 확인

문서가 오면 메인 세션이 읽고, 와이어프레임이 확정 시안과 다른 곳이 있으면 고치게 한다. 사용자에게는 문서 전체가 아니라 **상태 표만** 쉬운 말로 보여 주고 확인받는다. 예: "데이터가 없을 때는 '아직 기록이 없어요'와 추가 버튼을 보여 줘요. 괜찮나요?"

구현은 이 모드의 범위가 아니다. spec 문서를 입력으로 `/private-implement` 를 안내한다.
