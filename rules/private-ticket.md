## 티켓 분해 원칙 — 의존성·병목 최소화

티켓은 **서로의 의존성과 병목을 최소화**하도록 작성한다. 병렬 작업 가능성이 클수록 좋은 분해다. 구현자는 사람이 아니라 **에이전트 팀**(implementer 동시 스폰)이므로, wave 너비가 곧 병렬 처리량이다.

### 좋은 분해
- 한 티켓 = 한 책임. 다른 티켓의 클래스/스키마를 기다리지 않아도 시작 가능
- 공통 인터페이스·DTO·상수는 **선행 티켓**으로 별도 분리
- 도메인이 다르면 티켓도 분리, 레이어가 다르면 가능한 분리

### 안 좋은 분해 (수정 필요)
- 한 티켓에서 3개 이상 도메인을 동시에 건드림 → 도메인별 분리
- 후행 티켓 5개 이상이 선행 의존하는 거대 티켓 → 공통 부분 추출 + 도메인별 후속 티켓
- "전체 마이그레이션" 같은 단일 티켓 → 단계별 분리

### 불가피한 병목 — 연관 병목은 하나로 묶는다 (직렬 사슬 방지)

후행 티켓이 import/참조해야 하는 공통 산출물(공통 코드·스키마·설정·인프라)은 분리할 수 없는 병목이다. **단일 선행 티켓**으로 분리하고 의존 관계를 명시한다.

- **연관(결합)된 병목 → 하나의 선행 티켓으로 합친다.** 서로 의존하거나 같은 파일을 건드리는 공통 산출물을 쪼개면 wave가 1→1→1 직렬 사슬이 되거나 머지 충돌이 난다. "공통 계약 확립"을 한 책임으로 묶어 한 wave에 끝내고, 후행 N개를 트리형으로 동시에 연다.
- **독립적인 병목 → 쪼개 fan-out을 넓힌다.** 서로 의존하지 않고 다른 파일을 건드리는 공통 산출물은 별도 선행 티켓으로 분리해 wave 1을 넓힌다.

> 목표 모양: **연관 병목 1개(선행 wave) → 독립 후행 N개(트리형 병렬 wave)**

### Fan-out 너비 목표 (강제 게이트)

- 분해 결과를 위상정렬해 **wave별 너비 분포를 산출물에 반드시 포함**한다.
- **모든 wave 너비가 1~2인 직선형 DAG는 분해 실패** — 재분해 전 구현 진행 금지. 거대 병목을 (독립 단위로) 더 쪼개거나 도메인 경계를 다시 그린다.
- 후행 의존 카운트 ≥ 3인 티켓은 분해 재검토 트리거 — 단 **독립적인** 하위 산출물만 쪼갠다.

### Single Writer per File (한 파일 = 한 티켓)

같은 wave의 두 티켓이 동일 파일을 수정하면 머지 충돌이 난다. 분해 직후 확인:

1. **수정 예상 파일 집합 추정** — 티켓별 대상 파일을 패키지·설정 단위로 적는다.
2. **같은 wave 내 교집합 ∅ 검증** — 교집합이 있으면 분해 실패.
3. **공통 파일 수정 분리** — 라우터 등록·와이어업·공통 설정은 별도 **통합 티켓**으로 추출해 마지막 wave 단독 배치.

| 작업 유형 | 배치 |
|---|---|
| 도메인 서비스 신설 (새 패키지) | 같은 wave OK |
| 공통 컨트롤러·라우터 와이어업 | 마지막 wave 단독 통합 티켓 |
| 공통 설정 (application.yml, build.gradle.kts) | 선행 wave 단독 또는 통합 티켓 |
| 공유 컴포넌트 | 정의는 선행 단독, 사용은 후행 도메인별 |

- {선행 티켓 ID 목록 — 없으면 "없음"}

## 조건부 포함 — 롤백

상태 전이·DB 마이그레이션·파괴적 변경·외부 연동을 포함하는 티켓은 **작업 내용에 롤백 방법 1줄 명시**. 예: "마이그레이션 실패 시 역방향 DDL로 컬럼 제거", "피처 플래그 OFF로 즉시 비활성화". 단순 추가·내부 리팩토링은 생략.

## 포함하지 않는 것

- **AC(인수 조건)**: 테스트 케이스가 그 역할을 한다.
- **생성/수정 파일 목록**: 코드베이스가 기준 (Single Writer 검증용 추정은 분해 산출물에만).

## 코드 / SQL

설계 의도는 다이어그램과 텍스트로 표현. 코드·SQL은 텍스트로 표현 불가한 경우(복잡한 쿼리 조건·마이그레이션 DDL)에만 `<details>` 숨기기 섹션에 포함.

## 테스트 케이스 작성 기준

- 각 케이스 **한 문장**, Given/When/Then 풀어쓰기 금지. 티켓당 **최소 3개** — 책임 범위가 넓을수록 더 많이.
- 다이어그램의 분기·예외 경로마다 대응 케이스가 있어야 한다.

| 유형 | 예시 |
|---|---|
| 해피 패스 | "ABOVE 방향 알림이 목표가에 도달하면 TRIGGERED로 전이된다" |
| 실패·예외 | "401 응답 시 토큰을 재발급하고 1회 재시도한다" |
| 엣지·경계값 | "동일 symbol 중복 추가 시 멱등하게 처리된다" |
| 상태 보호 | "TRIGGERED된 알림은 재평가 대상에서 제외된다" |

## 패키지 이전 티켓 (금지 패턴)

패키지 리네임/이전 티켓은 다음을 작업 범위에 명시한다: Port 인터페이스 제거·단순 위임 Adapter 제거·Anemic Entity 재배치·구 패키지 import 100% 갱신(구 디렉토리 0 파일)·typealias 금지. **"디렉토리 이동 + package 선언 변경"만 적힌 티켓은 분해 단계에서 반려.**
