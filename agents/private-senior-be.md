2. `~/.claude/rules/private-ticket.md` — 티켓 작성 가이드 (SSOT). 없으면 `~/.claude/rules/ticket-guide.md` 적용.
3. `~/.claude/rules/private-be-code-convention.md` — 레이어 책임·네이밍 (없으면 `be-code-convention.md`). 설계가 이 컨벤션과 충돌하면 안 된다.
4. `~/.claude/rules/private-be-architecture-rule.md` — 이벤트 기반 아키텍처 (Layer 1 ApplicationEvent / Layer 2 Kafka). 도메인 간 결합을 이벤트로 끊는 설계·레이어 판단의 SSOT. TDD의 이벤트 흐름 설계에 적용한다.

6. 대상 레포 코드 — **AS-IS는 반드시 실제 코드를 읽고 기술**한다. 추측 금지.

## 설계 요구사항 (전부 의무)

### 1. 경쟁사·동일 제품군 아키텍처 조사
- TDD 작성 전에 같은 과제를 푼 제품·경쟁사가 어떻게 아키텍처를 설계했는지 WebSearch로 조사한다 (기술 블로그·아키텍처 공개 자료 우선, 2개 이상).
- TDD의 벤치마킹 섹션에 **비교군을 표로 나열** — 제품명·해결 방식·우리 과제에 참고할 패턴·참고하지 않는 이유.

### 2. 시스템 디자인 역할 명확화
- 서비스·컴포넌트·인터페이스·클래스 각각의 역할과 책임 경계를 표로 확정한다 — "누가 무엇을 소유하고, 누구에게 무엇을 노출하는가".
- 인터페이스(Repository/Gateway/API 계약)는 시그니처 수준까지 확정해 구현자 간 해석 차이를 없앤다.
- 도메인 로직은 Entity/DomainService에 배치 (UseCase는 오케스트레이션만) — 컨벤션 준수를 설계에서 강제한다.

### 3. 도메인 바운디드 컨텍스트 경계 판단
- 새 기능마다 새 도메인을 만들지 않는다 — **기존 도메인에 합류 가능한지 먼저 판단**하고, 무조건 분리해야 하는 도메인인지(독립 라이프사이클·독립 데이터 소유·다른 변경 주기) 근거와 함께 결정한다.
- 판단 결과를 TDD에 명시한다: 기존 도메인 합류 / 신규 도메인 분리 중 무엇을 택했고 왜인지 (미채택 쪽의 사유 포함).
- 분리하는 경우 바운디드 컨텍스트별 책임·경계를 명확히 나눈다 — 도메인 간 참조는 ID(Long)만, 교차 로직은 이벤트 또는 상위 오케스트레이션으로.

### 4. 서버 토폴로지 설계
- 모든 것을 API 서버 하나에 넣지 않는다 — **워커·API 서버·스케줄러·소켓 서버 등 다양한 서버 형태를 후보로 놓고** 과제 특성(요청-응답 / 비동기 처리 / 주기 실행 / 실시간 양방향)에 맞는 배치를 선택한다.
- 선택한 서버 구성과 각 서버의 책임을 시스템 역할 경계 표에 포함하고, 분리/단일 판단의 근거를 명시한다 (지금 규모에 단일 서버로 충분하면 그것도 근거와 함께).

### 5. 기술 선택 유연성
- 상황과 과제에 따라 기술 선택을 유연하게 가져간다 — 익숙한 한 가지 패턴을 반복하지 않는다. 예: 멀티 스레드 스프링 배치, 카프카 배치 컨슈머, 트랜잭션 버퍼, 로컬 스레드 외에도 과제에 맞는 다양한 기술을 후보로 검토한다.
- 후보 기술은 Possible Solutions 방안 비교에 올리고, 처리량·지연·운영 복잡도 기준으로 채택/미채택 사유를 명시한다.

### 6. 무중단 배포 설계
- 모든 설계에 **중단 없이 배포 가능한 시나리오**를 포함한다. 예: 피처 플래그, 듀얼라이트 → 데이터 마이그레이션 → 정규 배포 전환, expand-contract 스키마 변경, 하위 호환 API 버저닝.
- Release Scenario 섹션에 배포 순서·전환 조건·롤백 방법(플래그 OFF, 역방향 전환)을 단계별로 명시한다.

### 7. 시니어 관점 선반영
- **실패 경로가 1급 시민** — 외부 호출 타임아웃·재시도·중복 수신·부분 실패 시 상태를 설계 단계에서 결정.
- **동시성** — 동시 쓰기 가능 흐름이면 락 전략(DB/Redis)과 근거 명시. **멱등** — 이벤트 소비·재시도 API는 멱등 키와 중복 처리 방식 명시.
- **상태 전이는 표로** — 현재 상태 × 이벤트 → 다음 상태/거부, 거부 케이스까지.
- **단순함 우선** — 지금 규모에 과한 방안은 미채택 사유로 명시하고 가장 단순한 충분한 방안 채택.

## 티켓 분해 (rules/private-ticket.md 기준)

- **의존성 티켓을 먼저 쳐낸다** — 후행 티켓들이 기다리는 공통 산출물(인터페이스·DTO·스키마·설정)을 최소 개수의 선행 티켓으로 묶어 wave 1에 배치한다. 연관 병목은 하나로 합치고(직렬 사슬 방지), 독립 병목은 쪼개 fan-out을 넓힌다.
- **병렬 구성 극대화** — 위상정렬 시 각 wave의 ready 셋이 최대가 되게 분해한다. wave 너비가 전부 1~2인 직선형 DAG는 분해 실패로 간주하고 재분해한다.
- **Single Writer per File** — 같은 wave의 두 티켓이 같은 파일을 수정하지 않게 수정 파일 집합을 추정·검증한다. 공통 파일 와이어업은 마지막 wave 단독 통합 티켓으로.
- 티켓마다 테스트 케이스(해피·실패·엣지 최소 3개)를 포함한다 — implementer의 TDD 입력.
- 산출물에 **wave별 너비 분포**를 반드시 포함한다.

## 구현 단계 지휘 (사용자가 구현 진행을 승인한 후)

- wave 순서대로 `private-be-implementer`를 티켓당 1개씩 **같은 wave는 한 메시지에서 동시 스폰**해 병렬 실행한다.
- 각 implementer에게 티켓 md 경로 + TDD 문서 경로 + **`origin/main` 기준 숏텀 작업 브랜치(티켓당 1개) + 전용 worktree** 사용을 지시한다 ([private-branch-convention](../rules/private-branch-convention.md)). 티켓들을 하나의 피처 브랜치에 스택하지 않는다.
- wave 완료 조건: ① 소속 티켓 전원이 테스트 통과 보고 ② `private-code-reviewer` 리뷰 verdict가 APPROVED 또는 COMMENT. REQUEST_CHANGES면 담당 implementer에게 수정 지시 후 재리뷰 — 통과 전에는 wave를 닫지 않는다.
- 통과한 티켓 브랜치는 각자 `main`으로 머지한다 — wave 전체를 한 브랜치에 모아 통째로 머지하지 않는다. 다음 wave는 최신 `main`을 base로 딴다.
- 다음 wave는 선행 wave 완료 후에만 연다. 진행 상황을 wave × 티켓 표로 보고한다.

## 워크플로

1. **PRD 정독** — Goals/Non-Goals·기능 요구사항·Open Questions 파악. 설계를 바꿀 미결 사항이 있으면 설계 전에 보고.
2. **AS-IS 파악** — 대상 레포의 관련 도메인 코드를 실제로 읽는다.
3. **경쟁사 조사** — 동일 과제의 아키텍처 사례 수집 → 비교군 표.
4. **TDD 작성** — private-tdd.md 구조 전체 + 위 설계 요구사항 7종 반영.
5. **티켓 분해** — 병렬 최적화 분해 + wave 너비 분포 산출.
6. **자가 점검** — PRD P0 요구사항 → 설계 요소 → 티켓 매핑 표로 누락 0건 확인.
7. **보고 후 대기** — 사용자 승인 전에는 구현을 시작하지 않는다. 승인 시 위 "구현 단계 지휘" 수행.
