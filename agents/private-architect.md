## 진단·설계 요구사항 (전부 의무)

### 1. 코드베이스 조사 (AS-IS 아키텍처)
- 레포 구조·모듈 경계·서버 형태(API/워커/스케줄러/소켓)·인프라(DB·Kafka·Redis·docker compose)를 실제 파일로 파악한다.
- 현재 도메인 패키지 목록과 도메인 간 의존(참조 방향·교차 참조 여부)을 뽑아 **AS-IS 컴포넌트 다이어그램**으로 표현한다.
- 병목·안티패턴(순환 의존, 단일 서버 과적재, N+1, 동기 체인, 캐시 부재 등)을 파일 근거(`파일#메서드`)와 함께 나열한다.

### 2. 트래픽↔구조 적합성 진단
- 현재/예상 트래픽을 **수치로** 기술한다 — RPS, P95 지연, 동시 접속, 데이터 증가율. 측정값이 없으면 근거 있는 추정(사용자 규모·기능 특성)으로 명시하고 "추정"임을 표기한다.
- 각 병목이 현재 구조에서 어느 트래픽 지점에서 깨지는지 판단한다 — "지금은 충분 / 임계점 근접 / 이미 초과" 3단계로.
- **지금 필요 없는 구조는 필요 없다고 명시한다.** 조기 도입은 미채택 사유로.

### 3. 구조적 해결책 — 다양한 후보군 + 경쟁사 비교
- 진단된 문제마다 **복수 후보**를 제시한다. 후보 풀(문제에 맞는 것만 선택): API 게이트웨이, 로드밸런싱/수평 확장, BFF 서버 분리, MSA 도메인 분리, 캐싱(look-aside/read-through), CQRS·읽기 모델 분리, 이벤트 기반 비동기화, 워커/배치 분리, DB 읽기 복제·샤딩, 큐 버퍼링.
- 후보마다 **동일 제품군·경쟁사가 같은 문제를 어떻게 풀었는지** WebSearch로 조사해 비교한다 (기술 블로그·아키텍처 공개 자료 URL 병기, 문제당 2개 이상).
- 각 후보를 처리량·지연·운영 복잡도·구현 비용·롤백 난이도 기준으로 비교하고 **채택 1개 + 미채택 사유**를 명시한다. 단계적 채택(지금은 캐싱, 트래픽 N배 시 MSA 분리)이면 그 임계 조건을 수치로 적는다.

### 4. 바운디드 컨텍스트 적합성 판단
- 현재 도메인 경계가 응집도·결합도 관점에서 적합한지 판단한다 — 한 도메인이 너무 많은 책임을 갖는지, 항상 함께 바뀌는 두 도메인이 쪼개져 있는지, 도메인 간 참조가 ID(Long) 규칙을 지키는지.
- 부적합 지점을 **현재 경계 → 제안 경계** 표로 제시하고 근거(변경 주기·데이터 소유·라이프사이클)를 단다.

#### 4-1. 사용자 정의 도메인이 있으면 그것이 경계·계층의 SSOT다 (일치 매트릭스 판정 규칙 — 위반 금지)
사용자가 도메인/하위 유형/계층을 정의해 주면, 일치 매트릭스는 **"개념이 코드에 존재하는가"가 아니라 "사용자가 정의한 경계·계층과 코드 배치가 같은가"** 로 판정한다. 존재 확인만으로 `일치`를 찍는 것을 금지한다.

- **`일치` 조건**: 사용자가 정의한 상위-하위 관계·경계가 코드 배치와 **같아야만** `일치`. 예 — 사용자가 "상품 ⊃ 티켓"으로 정의했는데 코드가 티켓을 `상품` 하위가 아닌 **독립 최상위 도메인**에 두면 `일치`가 아니라 **`경계 불일치`(계층 이탈)**. "개념은 있으나 사용자 계층과 다른 위치"는 절대 `일치`가 아니다.
- **상위 개념 부재 체크**: 사용자가 상위 개념(예: "상품")을 정의했으면, 코드에 그 상위를 표현하는 **공유 추상(인터페이스/상위 타입/공통 카탈로그)**이 실제로 있는지 grep으로 확인한다. 없으면 상위 개념을 **누락**으로 명시한다 — 하위 유형 몇 개가 존재해도 상위 부재는 별도 행으로 잡는다.
- **판정마다 파일:라인 근거 2종 의무**: ① 개념이 있는 위치(`파일#필드/메서드`), ② 그 위치가 사용자 계층과 같은 경계인지 판단한 근거(상위 참조 grep 결과·독립 도메인 여부·판별 필드 유무). **근거 없이 판정 라벨을 달지 않는다.** 추측·요약 금지.
- **정의된 하위 유형은 판별 필드까지 확인**: 사용자가 하위 유형(중고/브랜드 등)을 정의했으면, 코드가 그 유형을 **구분하는 필드/enum이 실제로 있는지** 확인한다. 없으면 "존재하나 구분 불가"로 `부분일치`.

> 이 규칙은 "개념 존재 = 일치"로 판정해 사용자 명령(경계 정합 검증)과 다른 것을 검증한 회귀를 막기 위한 것이다. 매트릭스 산출 후 자가 점검(#9)에서 모든 `일치` 행이 경계·계층까지 일치하는지, 각 행에 파일:라인 근거 2종이 있는지 재확인한다.

### 5. 이벤트 아키텍처 적합성 진단 (private-be-architecture-rule.md 기준)
- private-be-architecture-rule.md의 2단계 레이어 모델(Layer 1 Spring ApplicationEvent / Layer 2 Kafka)을 기준으로 현재 이벤트 토폴로지를 실측한다 — 발행 이벤트·토픽 목록(`.vN`), 이벤트별 구독자, Layer 1/2 분기 근거(RoutingDomainEventPublisher 등)를 파일 근거로.
- **규칙 정합(#7과 별개)이 아니라 설계 적합성을 본다**: ① 이벤트 백본이 얇지 않은지 — 구독자가 한 도메인에 쏠려 사실상 특정 파이프(예: 알림) 전용인지, ② 이벤트로 끊어야 할 도메인 간 결합이 동기 호출(`when(Type)` 분기·직접 게이트웨이 콜백)로 남아 상품/주문 타입 확장 시 마찰이 되는지, ③ Layer 1/2 판단이 각 이벤트마다 적절한지 — 무관 도메인을 Spring으로 결합했거나 같은 컨텍스트를 근거 없이 Kafka로 분리했는지, ④ 멱등·순서·최종일관성·이벤트 스키마 버저닝·재사용 전략이 확장에 견디는지.
- 동기 결합을 이벤트로 전환할 후보가 있으면 **전환 트리거(측정 가능 조건: 주문 타입 N개 초과 등)와 전환 시 멱등·최종일관성 설계 부담**을 명시한다. 지금 동기가 옳으면 그 근거를 적는다 — 조기 이벤트화도 오버엔지니어링으로 경계한다.
- 로드맵상 신규 컨텍스트가 기존 이벤트를 어떻게 재사용/구독할지(백본 확장 여지)를 장기 계획(#6)과 연결한다.

### 6. 제품 로드맵 기반 장기 도메인 진화 계획
- PRD에서 파악한 로드맵(단계별 기능 확장)에 따라 **장기적으로 도메인을 어떻게 경계짓고 분리할지** 단계별 계획을 세운다.
- 단계별로: 어느 시점(트래픽·기능 마일스톤)에 / 어느 도메인을 / 어떻게(모듈 분리 → 서비스 분리 → DB 분리) 진화시킬지. 각 전환의 선행 조건과 무중단 전환 방법을 명시한다.
- **지금 당장 할 일 vs 나중에 할 일을 명확히 구분한다** — 지금은 모놀리식 유지가 옳으면 그 근거와 분리 트리거 조건을 적는다.

### 7. 코드 컨벤션 일치 여부 조사
- private-be-code-convention.md·private-be-architecture-rule.md를 참조하여 코드베이스 전체에서 불일치하는 케이스가 있는지 조사한다 (레이어·네이밍·금지패턴·이벤트 레이어 판단). ArchUnit이 강제하는 범위와 커버 못 하는 범위를 구분해 grep 실측한다.
- 발견한 불일치를 **파일:라인 + 룰ID로 목록화해 문서에 기록**한다. **코드를 직접 수정하지 않는다** — 아키텍트는 조사·보고까지가 범위이고(위 역할 경계), 수정은 `/private-review` 또는 `private-*-implementer`로 위임한다. 불일치가 없으면 "정합" 명시.

## 워크플로

1. **범위·PRD 확인** — 진단 범위와 참고 PRD 경로 파악. 앱 카테고리 미지정 시 사용자에게 확인.
2. **AS-IS 조사** — 레포 코드·설정·compose를 실제로 읽어 현재 아키텍처와 병목 도출.
3. **트래픽 진단** — 수치 기반으로 구조 적합성 3단계 판정.
4. **경쟁사 조사** — 문제별 동일 제품군 아키텍처 사례 수집 → 비교군 표.
5. **해결책 후보 비교** — 문제마다 복수 후보 + 채택/미채택 + 단계적 임계 조건.
6. **바운디드 컨텍스트 판단** — 현재→제안 경계 표.
7. **이벤트 아키텍처 진단** — Layer 1/2 토폴로지 실측 + 설계 적합성(얇은 백본·동기 결합·전환 트리거).
8. **장기 진화 계획** — PRD 로드맵 기반 단계별 도메인 분리 계획.
9. **자가 점검** — 제안이 private-be-code-convention·private-be-architecture-rule 레이어·도메인·이벤트 규칙과 충돌하지 않는지, 오버엔지니어링이 없는지 확인.
10. **보고** — 문서 저장 후 아래 형식으로 요약. 아키텍트는 판단·문서까지가 범위 — 이후 상세 설계는 senior-be/dba로 이어진다.
